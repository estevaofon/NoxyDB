# NoxyDB v0.1 — Design

## Objetivo

Construir, inteiramente em Noxy, um banco local, persistente, single-process e
single-node de `string` para `string`. A v0.1 deve oferecer criação, abertura,
`put`, `get`, `remove`, `exists`, fechamento e reconstrução do estado por replay
de um append-only log.

Ficam fora desta versão: rede, concorrência, múltiplos processos, transações,
replicação, sharding, índices secundários, TTL, autenticação, compaction,
checksums, reparo de logs e crash durability.

## Garantia de persistência

A v0.1 garante persistência após o fechamento normal do banco. `fsync`,
recuperação após interrupção de escrita e durabilidade diante de crash ficam
para versões posteriores.

## Modelo em memória

```noxy
struct LookupResult
    found: bool
    value: string
end

struct DatabaseState
    entries: map[string, string]
    file: io.File
    path: string
    open: bool
    error: string
end

struct Database
    state: DatabaseState
end
```

`DatabaseState` fica aninhado em `Database`. Como structs e maps são
heap-backed e a passagem comum faz cópia rasa do contêiner superior, o estado
aninhado permanece compartilhado entre a API e o chamador. Isso permite uma API
natural com `Database` por valor sem depender de `ref` através de membros de
módulo dinâmicos.

Os estados válidos são:

- `open == true && error == ""`: banco aberto;
- `open == false && error == ""`: banco fechado normalmente;
- `open == false && error != ""`: banco em estado de falha.

## API pública

```noxy
func open_database(path: string) -> Database
func put(db: Database, key: string, value: string) -> void
func get(db: Database, key: string) -> LookupResult
func remove(db: Database, key: string) -> void
func exists(db: Database, key: string) -> bool
func close_database(db: Database) -> void
func is_open(db: Database) -> bool
func database_error(db: Database) -> string
```

Chaves e valores vazios são válidos. `get()` retorna
`LookupResult(true, "")` para um valor vazio existente e
`LookupResult(false, "")` para uma chave inexistente. Assim, `get()` resolve
sozinho existência e valor; `exists()` é apenas uma conveniência.

`remove()` é usado no código Noxy para não sombrear o builtin `delete(map,
key)`. Uma interface textual futura poderá continuar chamando a operação de
`DELETE`.

Após fechamento normal ou falha, `put()` e `remove()` são no-op, `get()` retorna
não encontrado e `exists()` retorna `false`. `close_database()` é idempotente.

## Append-only log

Cada registro é uma linha ASCII terminada obrigatoriamente por `\n`:

```text
P\t<chave UTF-8 em hexadecimal>\t<valor UTF-8 em hexadecimal>\n
D\t<chave UTF-8 em hexadecimal>\n
```

Exemplo:

```text
P\t6c616e6775616765\t4e6f7879
P\t76657273696f6e\t31
D\t617574686f72
```

O hexadecimal permite qualquer string, incluindo `""`, Unicode, tabs e
quebras de linha, sem escaping próprio. Hexadecimal válido tem comprimento par
e contém apenas `0-9`, `a-f` ou `A-F`. Essa validação deve ocorrer antes de
`hex_decode`, pois o builtin retorna bytes vazios tanto para hexadecimal
inválido quanto para uma entrada vazia válida.

## Escrita

`put()` acrescenta sempre um registro `P`, inclusive em sobrescritas.
`remove()` acrescenta um tombstone `D` somente quando a chave existe; remover
uma chave ausente é no-op.

A ordem obrigatória é:

1. acrescentar o registro completo ao log;
2. somente após sucesso, alterar o map em memória.

Se uma escrita falhar, o map não deve mudar, `error` deve se tornar
`"failed to write database log"`, `open` deve se tornar `false` e nenhuma
operação posterior deve ser aceita nesse banco.

## Abertura e replay

`open_database()` cria um map vazio, reproduz um arquivo existente e somente
depois abre o arquivo em modo append. Um caminho inexistente representa um
banco novo. Um arquivo existente e vazio é válido.

O replay aplica registros em ordem. `P` insere ou sobrescreve; `D` remove a
chave se presente. A última operação determina o estado final.

O replay é estrito:

- toda linha, inclusive a última, deve terminar com `\n`;
- última linha sem `\n` é um log truncado;
- operação desconhecida, quantidade incorreta de campos ou hexadecimal
  inválido é um registro inválido;
- registros inválidos nunca são ignorados;
- a v0.1 não trunca, repara ou recupera automaticamente o arquivo;
- diante de falha, o arquivo não é aberto para append e o estado parcialmente
  reconstruído não fica utilizável.

Erros públicos previstos:

```text
failed to read database log
truncated database log
invalid database log record
failed to open database log for append
failed to write database log
failed to close database log
```

## Fechamento

No fechamento normal, o handle é fechado e `open` se torna `false`, mantendo
`error == ""`. A evolução aditiva de I/O aprovada abaixo tornará a falha
observável; nesse caso, o banco permanece fechado e expõe
`failed to close database log`.

## Tratamento de erros e limitação da Noxy

### Necessidade do NoxyDB

Detectar falha ao acrescentar um registro e somente então atualizar o map. Em
caso de falha, expor `failed to write database log`, fechar logicamente o banco
e rejeitar operações posteriores. Seria desejável observar também falha de
fechamento.

### Estado atual da Noxy

`io.write(file, content)` e `io.close(file)` retornam `void`. Na VM,
`io_write` chama `Write`/`WriteString` sem verificar o retorno ou o erro, e
`io_close` chama `Close` sem verificar o erro. Não há `flush` ou `fsync` público.

### Limitação

Código escrito em Noxy não consegue distinguir uma escrita ou um fechamento
bem-sucedido de uma falha. Por isso, não é possível implementar fielmente a
semântica de `failed to write database log` com a Noxy atual. O restante da
v0.1 é implementável sem mudanças na linguagem.

### Solução aprovada

A menor mudança razoável aprovada é adicionar operações observáveis à stdlib,
sem mudar sintaxe, compilador ou modelo de erros da linguagem:

```noxy
struct IOWriteResult
    success: bool
    bytes_written: int
    error: string
end

struct IOCloseResult
    success: bool
    error: string
end

func write_result(file: File, content: string) -> IOWriteResult
func close_result(file: File) -> IOCloseResult
```

As operações atuais permanecem compatíveis. As novas operações expõem somente
o resultado e a contagem que a implementação Go já fornece; não adicionam
`fsync` nem ampliam a garantia de durabilidade. NoxyDB usa as variantes
observáveis.

## Testes

Os testes Noxy usam as funções públicas reais e encerram o processo com código
diferente de zero quando uma asserção falha. Um runner PowerShell executa cada
arquivo em processo separado, limpa apenas os artefatos de teste conhecidos e
confirma o código de saída.

Cobertura mínima:

1. inserir e recuperar;
2. sobrescrever;
3. consultar chave inexistente;
4. armazenar e distinguir valor vazio;
5. remover;
6. `exists()` para presença e ausência;
7. múltiplas chaves;
8. fechar e reabrir em outro processo;
9. tombstone preservado após reinício;
10. várias alterações sobre a mesma chave, incluindo `1`, `2`, `3`, remoção e
    `4`;
11. banco vazio;
12. última linha truncada;
13. operação, aridade de campos e hexadecimal inválidos;
14. fechamento idempotente e operações rejeitadas após fechamento;
15. falha de abertura para append.

O teste de falha efetiva de escrita usa `write_result` sobre um handle cujo
descritor subjacente não aceita mais escrita. Ele confirma que o map não muda e
que o banco entra em `failed to write database log`.

## Critérios de conclusão

- todo código do banco é Noxy;
- nenhuma mudança é feita na linguagem, VM ou stdlib sem aprovação separada;
- os testes automatizados passam com a implementação atual da Noxy;
- o estado recuperado corresponde exatamente à sequência válida do log;
- os limites de durabilidade e detecção de erro são documentados sem promessas
  superiores às capacidades da plataforma.
