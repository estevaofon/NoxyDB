# NoxyDB v0.2 Documents — Design

## Status

Approved on 2026-08-12.

## Goal

Evolve NoxyDB from `string -> string` to `string -> document`, where every
document is a JSON object represented in public Noxy code as
`map[string, any]`. Preserve the append-only storage engine and its failure
semantics while keeping JSON knowledge entirely above `storage.nx`.

The v0.2 API and physical format make no compatibility promise to v0.1. There
is no migration, fallback, format header, version discriminator, or legacy
value handling.

## Non-goals

The v0.2 does not add field queries, JSON Path, partial updates, secondary
indexes, schemas, a query engine, collections, filters, compaction, TTL,
networking, concurrency, transactions, replication, or sharding.

Crash durability also remains outside this milestone. Persistence is promised
after `close_database()` completes successfully; the database does not call
`fsync`.

## Architectural decisions

The v0.2 uses these boundaries:

```text
NoxyDB public API
    key -> map[string, any]
             |
             v
document.nx
    strict serialize / validated deserialize
             |
             v
DatabaseState.payloads
    map[string, string]
             |
             v
storage.nx
    key -> opaque serialized payload
             |
             v
append-only P/D log
```

The authoritative in-memory value is the serialized JSON string, not a decoded
map. This is required by Noxy's shallow-copy semantics: nested arrays, maps,
and structs retain shared identity across ordinary copies. Retaining decoded
documents would permit a caller to mutate database state without executing
`put()` and without appending to the log.

`put()` serializes immediately and stores only the resulting string. `get()`
deserializes on every successful lookup and returns a newly allocated map.
Mutating either the original input after `put()` or a value returned by `get()`
cannot alter the authoritative state.

## JSON document model

### Root

Every document must be a JSON object. The public representation is written
directly as:

```noxy
map[string, any]
```

Noxy has no type alias or recursive union suitable for a nominal `JsonValue`.
The v0.2 does not change the type system to add one. A `Document` wrapper struct
is also intentionally omitted because it would add a `.fields` access layer
without materially strengthening the contract.

The function signature itself rejects strings, numbers, booleans, null, and
arrays at the root. These values remain valid recursively inside the root map.

### Value mapping

| JSON value | Noxy representation |
| --- | --- |
| string | `string` |
| integral number | `int` (signed 64-bit) |
| fractional number | finite `float` (64-bit) |
| boolean | `bool` |
| null | `null` stored through `any` |
| array | a Noxy array; use `any[]` for heterogeneous arrays |
| object | `map[string, any]` |

Nested arrays and objects recursively use the same mapping. NoxyDB accepts the
numeric domain representable by Noxy: signed 64-bit integers and finite
64-bit floating-point values. It does not provide arbitrary-precision JSON
numbers.

### Strict JSON domain

Serialization accepts only:

- `null`;
- `bool`;
- `int`;
- finite `float`;
- `string`;
- arrays containing only accepted values;
- maps whose every key is a string and whose every value is accepted.

Serialization rejects bytes, structs and struct definitions, references,
functions, native functions, channels, wait groups, non-string map keys,
NaN, positive or negative infinity, unsupported runtime values, and cyclic
arrays or maps. Reusing the same acyclic child from more than one branch is
valid; only an identity present in the active traversal path is a cycle.

## Public types and API

```noxy
struct LookupResult
    found: bool
    value: map[string, any]
end

struct PutResult
    success: bool
    error: string
end

func open_database(path: string) -> Database
func put(db: Database, key: string, document: map[string, any]) -> PutResult
func get(db: Database, key: string) -> LookupResult
func remove(db: Database, key: string) -> void
func exists(db: Database, key: string) -> bool
func close_database(db: Database) -> void
func is_open(db: Database) -> bool
func database_error(db: Database) -> string
```

`LookupResult(true, {})` represents an existing empty document.
`LookupResult(false, {})` represents an absent key. `found` therefore remains
necessary.

`PutResult` separates an invalid caller document from a database failure:

| Condition | Result | Database state |
| --- | --- | --- |
| valid document persisted | `PutResult(true, "")` | remains open |
| non-JSON-compatible document | `PutResult(false, "document is not JSON-compatible")` | remains open and unchanged |
| database already closed or failed | `PutResult(false, "database is not open")` | unchanged |
| append failure | `PutResult(false, "failed to write database log")` | transitions to failed |

`remove()` retains its v0.1 idempotent semantics. Removing an absent key is a
no-op and does not append a tombstone.

## Authoritative state

```noxy
struct DatabaseState
    payloads: map[string, string]
    file_fd: int
    path: string
    open: bool
    error: string
end

struct Database
    state: DatabaseState
end
```

The valid lifecycle states remain:

- `open == true && error == ""`: open;
- `open == false && error == ""`: closed normally;
- `open == false && error != ""`: failed.

The database continues to retain the numeric file descriptor and reconstruct
transient `io.File` values at I/O boundaries. The existing workaround for
incomplete imported-struct runtime metadata remains local and does not affect
the document model.

## Document codec

A new `noxydb/document.nx` module owns all JSON knowledge.

```noxy
struct SerializeResult
    success: bool
    payload: string
    error: string
end

struct DeserializeResult
    success: bool
    value: map[string, any]
    error: string
end

func serialize(value: map[string, any]) -> SerializeResult
func deserialize(payload: string) -> DeserializeResult
```

`serialize()` invokes the new strict and observable stdlib encoder. It maps any
encoding rejection to `document is not JSON-compatible` and never returns a
fallback payload.

`deserialize()` creates an empty `map[string, any]` and uses the existing
observable `json_loads` target API. Success requires complete valid JSON and an
object at the root. A scalar, array, null, malformed JSON, trailing value, or
value that cannot populate the map returns `invalid document payload`.

The codec does not mutate caller-owned data. Each successful deserialize starts
from a fresh empty map.

## Strict observable JSON encoding in Noxy

The current `json_dumps(any) -> string` remains unchanged for compatibility
with existing Noxy programs. NoxyDB does not use it.

The stdlib gains a `json` module with:

```noxy
struct EncodeResult
    success: bool
    data: string
    error: string
end

func dumps_result(value: any) -> EncodeResult
```

The wrapper delegates to a VM native that performs a recursive checked
conversion and constructs `EncodeResult`. It returns success only when the
entire graph belongs to the strict JSON domain. No unsupported value is
stringified, no non-finite float is converted, and no error becomes the valid
JSON text `null`.

The encoder detects cycles by composite object identity along the active DFS
path. It removes identities when unwinding, so repeated acyclic references are
serialized normally.

This evolution changes the stdlib and VM only. It requires no lexer, parser,
AST, compiler, bytecode, or type-system changes.

## Write flow

`put(db, key, document)` executes in this order:

1. Reject a database that is not open.
2. Strictly serialize the document.
3. On serialization failure, return a failed `PutResult` without touching the
   log, state, or database lifecycle.
4. Append `P` with the key and serialized payload.
5. On append failure, preserve the previous payload, close the underlying file
   if possible, transition the database to failed, and return failure.
6. Only after append succeeds, assign `db.state.payloads[key] = payload`.
7. Return success.

Overwrite remains a complete document replacement. Partial updates are out of
scope.

## Read flow

`get(db, key)` executes in this order:

1. Return not found when the database is not open.
2. Return not found when the raw payload map lacks the key.
3. Deserialize the payload into a new map.
4. Return `LookupResult(true, value)` on success.

Every payload admitted by `put()` or validated during opening must deserialize
successfully. A defensive failure during `get()` indicates violated internal
state; it closes the database logically, records `invalid document payload`,
and returns not found.

## Open and replay flow

`open_database(path)` executes in this order:

1. Create an empty raw payload map.
2. If the path exists, call `storage.replay(path)`.
3. Reject any physical log error without exposing partial replay state.
4. Deserialize every replayed payload to validate the document invariant.
5. If any payload is invalid, return a failed database with
   `invalid document payload` and an empty authoritative map.
6. Only after complete validation, open the file in append mode.
7. Return an open database containing the replayed serialized payloads.

Decoded validation values are discarded. The database does not retain a
decoded cache.

## Storage engine and physical log

`storage.nx` operates on opaque strings and must not import or invoke JSON
functionality.

```noxy
struct ReplayResult
    success: bool
    payloads: map[string, string]
    error: string
end

func replay(path: string) -> ReplayResult
func append_put(file: io.File, key: string, payload: string) -> io.IOWriteResult
func append_remove(file: io.File, key: string) -> io.IOWriteResult
```

The physical record grammar remains:

```text
P<TAB><key_hex><TAB><payload_hex>\n
D<TAB><key_hex>\n
```

This grammar is retained because it is technically suitable, not to preserve
v0.1 compatibility. Hexadecimal encoding keeps framing independent from keys
and payload contents, including Unicode, tabs, and newlines. The size overhead
is accepted in exchange for the simpler strict replay supported by the current
stdlib.

Replay remains strict:

- every record must end in `\n`;
- operation and field count must be exact;
- key and payload hexadecimal must be valid and even-length;
- records are applied in order;
- `P` inserts or overwrites the opaque payload;
- `D` removes the key if present;
- invalid, incomplete, or unreadable logs are never repaired or skipped;
- the read byte count must equal `io.stat(path).size`;
- the log is opened for append only after replay and document validation both
  succeed.

The storage engine classifies envelope corruption. The document layer
classifies decoded payload corruption.

## v0.1 behavior

The v0.2 contains no code that detects, converts, migrates, or recovers v0.1
values. A v0.1 database will normally fail document validation because its raw
strings are not JSON objects. An accidental old payload that is also a valid
JSON object does not create a compatibility guarantee.

No v0.1 fixture or compatibility test is retained.

## Error behavior

Existing storage and lifecycle errors remain:

```text
failed to read database log
truncated database log
invalid database log record
failed to open database log for append
failed to write database log
failed to close database log
```

The document layer adds:

```text
document is not JSON-compatible
invalid document payload
database is not open
```

An invalid input document is an operation error and does not fail the database.
An invalid persisted or authoritative payload violates the database invariant
and produces a failed database. I/O failures retain the v0.1 state-transition
semantics.

### Noxy repository

- Create `internal/stdlib/json.nx` for `EncodeResult` and `dumps_result`.
- Modify `internal/stdlib/embed.go` to expose the module.
- Modify `internal/vm/builtins_json.go` with strict recursive conversion and
  the observable native result.
- Modify JSON builtin, registry, native-signature, and stdlib integration tests.
- Update `docs/JSON_SUPPORT.md`.

### NoxyDB repository

- Create `noxydb/document.nx` for the codec.
- Modify `noxydb/noxydb.nx` for public types, raw state, serialization,
  deserialization, and replayed-document validation.
- Modify `noxydb/storage.nx` only to rename value concepts to opaque payloads;
  preserve the record grammar and replay mechanisms.
- Rewrite document-sensitive tests and assertions.
- Add document-domain, isolation, and invalid-payload tests.
- Update `README.md` to document the v0.2 API and format.

## Test strategy

Implementation follows test-driven development. Each behavior begins with a
focused failing test, receives the minimum implementation, and is followed by
focused and regression verification.

### Existing concepts retained

- new and empty database opening;
- open, closed, and failed states;
- idempotent close;
- append-before-memory;
- I/O write and close failure visibility;
- overwrite order;
- tombstones and removal persistence;
- replay of repeated history;
- strict record framing and hexadecimal validation;
- read byte-size validation;
- Unicode and control characters in keys;
- rejection of operations after close or failure.

### Existing tests rewritten

- all string-value lookups become document lookups;
- empty-string value coverage becomes a field containing `""`;
- persistence and history fixtures store full documents;
- internal assertions inspect `payloads`, never decoded entries;
- write-failure assertions compare the prior serialized payload or public
  document result.

### New Noxy encoder tests

- null, bool, minimum and maximum int, finite float, empty string, and Unicode;
- empty and nested arrays;
- empty and nested string-keyed maps;
- heterogeneous arrays through `any[]`;
- arrays of maps;
- bytes, structs, functions, native functions, channels, and non-string map
  keys rejected;
- NaN, positive infinity, and negative infinity rejected;
- direct array cycle, direct map cycle, and indirect composite cycle rejected;
- repeated acyclic child accepted;
- an encoding error returns `success == false`, non-empty `error`, and no
  fallback JSON payload;
- legacy `json_dumps` behavior remains unchanged.

### New NoxyDB document tests

- empty root object;
- empty string field;
- int and float fields;
- true and false fields;
- null field;
- empty and populated arrays;
- nested objects;
- arrays of objects;
- mixed and deeply nested structures;
- Unicode field names and values;
- complete document overwrite;
- removal;
- persistence and replay in separate processes;
- hex-valid record containing malformed JSON;
- scalar, array, and null JSON roots rejected during open;
- invalid Noxy value rejected by `put()` while the database remains open;
- failed serialization changes neither log nor raw state;
- failed append changes neither the prior raw payload nor its public document;
- mutating input after `put()` does not change stored data;
- mutating a `get()` result does not change a later `get()`;
- separate `get()` results do not share nested mutable state.

## Incremental implementation order

1. Add strict observable JSON encoder tests and implementation in Noxy.
2. Add `document.nx` codec tests and implementation.
3. Change public NoxyDB types and implement document `put()`/`get()` over raw
   in-memory payloads.
4. Adapt storage naming while preserving the physical record grammar.
5. Add replay-time document validation and invalid-payload behavior.
6. Rewrite persistence, tombstone, lifecycle, and I/O failure tests.
7. Add alias-isolation and complete document-domain coverage.
8. Update documentation and run full Noxy and NoxyDB verification.

## Acceptance criteria

- The public database contract is `string -> map[string, any]` with an object
  required at the root.
- `DatabaseState` retains only serialized JSON payloads.
- `storage.nx` contains no JSON knowledge.
- Every successful `get()` returns a newly deserialized document.
- Invalid input documents return a failed `PutResult` without failing or
  mutating the database.
- Append failure happens before and prevents raw-state mutation.
- Replay is strict at both the record-envelope and document layers.
- All required scalar, null, collection, nesting, Unicode, overwrite, removal,
  persistence, replay, and isolation tests pass.
- The strict encoder reports errors and rejects unsupported values, non-finite
  floats, and cycles without changing legacy `json_dumps`.
- No migration, fallback, version header, or v0.1 compatibility logic exists.
- No out-of-scope database feature is introduced.
